## Reason and scope

The macOS application now includes the native document-processing runtime that
the older, smaller application omitted. The task is to inventory reductions in
the Semantica release owner while preserving local PDF/table/OCR capabilities.
The older application is not an equivalent-capability size baseline.

The initial inventory was documentation only. The dated validation follow-up
below records isolated experimental artifacts; production runtime, dependency
declarations, model manifest, consumer pin and published artifacts remain unchanged.
The initial inventory statements and limitations below describe that earlier pass.

Do not add distribution totals to the four path totals without taking a union:
PyArrow and sklearn already contribute tests/headers to those path sets.

### Dependencies that are not deletion candidates on present evidence

- Torch and transformers serve the local Docling model path. The layout model
  (163.71 MiB) and ACCURATE table model (202.90 MiB) are capability-bearing assets.
- SciPy is also required by Docling's selected standard conversion/extraction
  extras. Removing Semantica's SciPy requirement alone would not remove SciPy.
- Pandas is required by docling-core and used by table/Excel parsing.
- OpenCV is required by RapidOCR; ONNX Runtime runs the admitted OCR backend.
- PyMuPDF remains the PDFParser owner. Do not restore pdfplumber or replace
  structured conversion with a second reader/pipeline to reduce size.
- `docling` and the pinned `docling-slim` implementation are a metadata package
  plus its implementation, not two full parser installations.

## Native capability assessment

- Bundle owner: `semantica/bundle.py::build_bundle`. It copies CPython, installs
  the wheel's selected semantic-worker extra, copies pinned models, removes
  generated bytecode, then computes inventory and parser/artifact digests.
- Model inputs: `.github/requirements/semantic-worker-models.json` and
  `.github/scripts/semantic_worker_models.py`; both table modes are explicit.
- Parser owners: `semantica/source.py::parse_source`,
  `semantica/parse/docling_parser.py::DoclingParser`,
  `semantica/parse/pdf_parser.py::PDFParser`.
- Installed Docling: `datamodel/pipeline_options.py` defaults to ACCURATE;
  `pipeline/base_pipeline.py` resolves explicit artifacts_path or
  settings.artifacts_path; `models/stages/ocr/rapid_ocr_model.py` has the
  fully offline packaged-artifact branch.
- Inspected callers: semantic worker/build/query modules; Arrow/Parquet
  ingestors/exporters and registrations; embedding visualization and Explorer.
- Tests/workflows: `tests/test_bundle.py`, `tests/test_semantic_worker_imports.py`,
  `tests/test_pyproject_extras.py`, `.github/scripts/semantic_worker_acceptance.py`,
  `.github/scripts/semantic_worker_model_acceptance.py`, and
  `.github/workflows/semantic-worker-native.yml`.
- The inspected bundle/source/parser/dependency files and the ingest/export/
  visualization/Explorer directories have no diff between local HEAD and fetched
  origin/main. Release acceptance scripts do differ; the fetched release version
  was inspected for the canonical SemanticArtifact contract.
- Decision: docs-only; any implementation must repair these native owners.
  No second implementation or host-side pruning layer is introduced.

## Approach and proposed sequence

1. Start with the model inputs: retain ACCURATE and prove offline PDF/table/OCR
   after excluding unused FAST assets and duplicate OCR weights. The two sets
   total 169.001 MiB before validation. Bind the model path/mode explicitly in
   the existing owner where required; do not silently switch algorithms.
2. Separate library capability dependencies from worker requirements using the
   existing extras. Update pyproject, uv.lock and native platform constraints
   together. Exercise Arrow/Parquet and visualization/Explorer install contracts
   with their extras as well as worker builds without them.
3. Review test/header paths package by package in build_bundle, before generating
   final inventories/digests. Do not strip arbitrary paths from host staging or
   modify an immutable published artifact after digest generation.
4. Reuse native GitHub Actions packaging, relocation and acceptance, publish a
   new immutable artifact, then update the host pin and measure the actual app.
